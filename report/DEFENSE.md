# Защита курсового проекта «Контур»

**Павленко Богдан Евгеньевич, ДЭ 21-25, 2 курс.** Рассчитай показ на 5–7 минут. До начала открой на компьютере учётную запись диспетчера, на телефоне — техника Михаила. По одному разу отрепетируй смену статуса и возврат к списку на каждом устройстве. В круглых скобках ниже указаны действия во время показа.

## Выступление с демонстрацией

**0:00–0:50. Задача.** «Тема моей работы — разработка клиент-серверного приложения для управления заявками на обслуживание оборудования. Представим аудиторию, в которой перед занятием перестал выводиться сигнал на проектор. Диспетчеру нужно понять, кому поручена работа, технику — найти аудиторию и узнать симптомы. После ремонта кто-то должен проверить результат. Для этого процесса разработан “Контур”. В демонстрационной базе есть шесть единиц оборудования, два техника и диспетчер. Все сведения учебные».

**0:50–1:50. Назначение.** (На ПК создай заявку «Проектор в аудитории 204 не выводит изображение», выбери проектор, высокий приоритет, назначь Михаила.) «Выбираю проектор из справочника. Его расположение уже указано в карточке. Высокий приоритет подскажет технику, с какой задачи начать. Статус “Назначена” означает, что за ремонт отвечает конкретный человек. Запомним номер заявки и найдём её на телефоне».

**1:50–3:05. Исполнение.** (Открой эту же заявку на телефоне. Нажми «Начать работу», добавь комментарий «Проверяю HDMI-вход». В результате напиши «Выбран вход HDMI 1, контрольное изображение появилось». Нажми «Завершить работу».) «На телефоне техник видит свои задания. Сервер берёт его идентификатор из подписанной сессии и ограничивает запрос к базе этим пользователем. Поэтому скрытие чужих карточек работает и при прямом обращении к их номерам. При завершении требуется описание результата. Комментарий может сообщать о ходе диагностики, а результат передаёт работу диспетчеру на проверку».

**3:05–3:55. Приёмка.** (Вернись на ПК. Если карточка была открыта, нажми «Обновить карточку». Покажи историю, найди текст результата, нажми «Подтвердить и закрыть».) «На двух экранах один и тот же номер. У событий есть автор и время. Сейчас видно, кто зарегистрировал работу, кто её начал и что было исправлено. Диспетчер завершает цикл приёмкой. Если изображение снова пропадёт, заявку можно вернуть исполнителю. Предыдущий результат останется в истории».

**3:55–5:00. Устройство системы.** (Покажи схему из главы 2.) «Браузеры работают с одним сервером по HTTP. Flask обрабатывает запросы, SQLite хранит данные на компьютере сервера. В базе четыре таблицы. Оборудование и пользователи существуют независимо от обращений. В заявке хранится текущее состояние, а в отдельной таблице событий — история. Когда техник меняет статус, запись заявки и событие сохраняются в одной транзакции. Если одна часть записи завершится ошибкой, система откатит обе. Для учебной системы этого достаточно, чтобы согласовать данные без отдельного сервера базы».

**5:00–6:10. Совместная работа и проверка.** «Представим, что два диспетчера открыли одну заявку версии 1. Первый изменил приоритет и сохранил версию 2. Второй по-прежнему отправляет запрос с версией 1. Сервер сопоставляет версии, возвращает 409 и сохраняет решение первого. Автообновление даёт пользователю увидеть изменения, а проверка версии защищает данные в промежутке между обновлениями. В тесте проверяются и ответ 409, и фактический приоритет после него, и число событий. В локальном прогоне прошли 36 тестов, включая сценарий полного цикла и проверку резервной копии. Итог работы — общий журнал заявок, в котором каждое разрешённое действие роли даёт проверяемое изменение».

## Вопросы, к которым стоит подготовиться

| Вопрос | Короткий ответ |
|---|---|
| Почему для проекта нужны два устройства? | Диспетчер находится у компьютера, а техник работает возле оборудования. Назначение, результат и приёмка относятся к одной записи, которую видно из обоих сеансов. |
| Как телефон находит сервер? | По локальному адресу компьютера и номеру порта. Оба устройства должны иметь сетевой маршрут друг к другу. На телефоне `localhost` указывает на телефон. |
| Почему выбран браузер? | Для работы на ПК и телефоне достаточно одного адреса и современной браузерной среды. Условие проекта трактуется как совместная работа на двух устройствах. |
| Почему четыре таблицы? | Пользователи и оборудование — справочники. Заявка — текущее состояние. Для одной заявки может быть много событий с разными авторами. |
| Как связаны заявка и оборудование? | `tickets.asset_id` ссылается на `assets.id`. Внешний ключ препятствует созданию записи с отсутствующим объектом. |
| Кто назначает автора события? | Сервер определяет вошедшего пользователя по сессии. Имя автора из тела запроса не принимается. |
| Чем приёмка отличается от выполнения? | Техник фиксирует результат и отдаёт работу на проверку. Затем диспетчер принимает или возвращает её. |
| Что делает транзакция? | Объединяет изменение заявки и запись истории. При ошибке во время записи изменения откатываются вместе. |
| Для чего версия, если в SQLite один писатель? | Записи могут идти по очереди, но вторая основана на старом экране. Версия позволяет обнаружить, что решение пользователя устарело. |
| Почему не увеличивается версия после комментария? | Добавляется отдельное событие. Поля самой заявки остаются прежними, поэтому такой комментарий не мешает сохранению изменения приоритета. |
| Откуда телефон узнаёт об изменениях? | Пока вкладка активна, клиент примерно раз в пять секунд запрашивает список и проверяет открытую карточку. Фактическая задержка зависит от сети и работы браузера. |
| Чем отличается проверка прав от CSRF? | Права определяют, какие заявки и операции разрешены вошедшему пользователю. Токен связывает изменяющий запрос с сеансом. Обе проверки выполняются сервером. |
| Что произойдёт при потере Wi-Fi? | Новые данные перестанут поступать. При неопределённом исходе отправки нужно переподключиться и проверить карточку и журнал перед повтором. |
| Почему SQLite? | Для стенда достаточно одного процесса и файла базы. Внешние ключи и транзакции доступны без отдельной службы. При высокой конкуренции записей потребуется оценить серверную СУБД. |
| Что подтверждено испытаниями? | Назови результат из главы 4, покажи конкретный сценарий. Прогон на физическом телефоне можно включить в устный ответ после собственной проверки в сети показа. |

## Как самому проследить одну операцию

Открой `app.py` и найди `update_ticket`. Проследи путь «версия → чтение доступной заявки → проверка роли и перехода → условный UPDATE → запись события → commit». Затем открой `tests/test_api.py`, функцию `test_optimistic_conflict_preserves_newer_data`. До чтения утверждений попробуй предсказать, какой приоритет и сколько событий получит первый пользователь после отказа второму. Для собственно показа достаточно следующей команды из активированного окружения:

```bash
python -m pytest -q tests/test_api.py -k 'two_devices_full_workflow or optimistic_conflict'
```
