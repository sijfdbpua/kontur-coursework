# Сервер «Контур»

## Запуск

Python 3.10+; проверяемая среда фиксируется в итоговом протоколе. Зависимости Flask 3.1.3 и Waitress 3.0.2. Сервер запускается через `python app.py serve --host 0.0.0.0 --port 8080`; исходный host без аргумента — `127.0.0.1`. Данные в `data/kontur.sqlite`, секрет подписи сессии в `data/session.key`. `KONTUR_DATA_DIR` меняет каталог обоих файлов. Не добавлять каталог данных в Git.

`python app.py init-demo` создаёт 6 единиц оборудования, 3 пользователей и 12 синтетических заявок. На непустой базе отказывается выполнять импорт. Учётные записи открыто указаны исключительно для учебной демонстрации:

| Логин | Пароль | Роль |
|---|---|---|
| dispatcher | demo-dispatch-2026 | Диспетчер |
| tech | demo-tech-2026 | Техник |
| tech2 | demo-tech2-2026 | Техник |

Это не система управления реальными сотрудниками: регистрации, смены пароля и администрирования учётных записей в интерфейсе нет. Для публичного применения нужны HTTPS, управление пользователями, резервное копирование, ограничения доступа и отдельная проверка безопасности.

## Обмен данными

Сначала `GET /api/session`: ответ `{user, csrf_token}`. Все POST/PATCH требуют `X-CSRF-Token`. Даже вход требует предварительного получения токена. После входа/выхода токен меняется; клиент должен сохранить новый. Авторизация хранится в подписанной HttpOnly cookie, SameSite=Lax, срок 8 часов с продлением при активности. Для HTTPS `KONTUR_HTTPS=1` включает Secure-cookie. HTTP разрешён только как осознанное ограничение демонстрации в доверенной локальной сети.

Все ошибки API имеют вид `{error: "Сообщение"}`. 400 — проверка входных данных/перехода, 401 — нужен вход, 403 — права/CSRF, 404 — нет доступной заявки, 409 — устаревшая версия, 413 — слишком большой запрос, 429 — лимит попыток входа, 503 — сбой SQLite. Подробности ошибок SQLite пишутся только в журнал сервера.

| Метод и адрес | Действие |
|---|---|
| GET /api/session | Текущая сессия и CSRF |
| POST /api/login | `{username,password}` → сессия |
| POST /api/logout | `{}` → анонимная сессия |
| GET /api/meta | `{users,assets}`; паролей/хешей нет |
| GET /api/tickets | `{tickets}`; техник видит только свои |
| GET /api/tickets/ID | `{ticket,events}` |
| POST /api/tickets | Создание диспетчером → `{ticket}`, 201 |
| PATCH /api/tickets/ID | Изменение с обязательным `version` → `{ticket}` |
| POST /api/tickets/ID/comments | `{body}` → `{event}`, 201 |
| GET /api/export.csv | Все заявки, только диспетчер |

Поля создания: `title` (1–160 символов), `description` (1–4000), `asset_id` (целое), `priority` (`low`, `normal`, `high`, `critical`), `assignee_id` (целое или null, необязательно). Неподдерживаемые поля отклоняются. Комментарий — 1–2000 символов. Результат работы — 1–4000. JSON — до 32 КиБ. Текст обрезается по краям; управляющие символы, кроме перевода строки и табуляции, запрещены.

Поля PATCH: `version`, `assignee_id`, `priority`, `status`, `resolution`. Изменение исполнителя и явного статуса одним запросом запрещено: это два разных действия.

## Переходы и согласованность

- Диспетчер назначает/снимает исполнителя только до начала работы: `new ↔ assigned`.
- Назначенный техник: `assigned → in_progress → done`. Для `done` обязателен результат.
- Диспетчер: `done → closed`; возврат `done/closed → assigned` сохраняет исполнителя, очищает текущий результат, но не историю.
- Диспетчер меняет приоритет любой незакрытой заявки.
- Техник не может переназначать, закрывать, менять приоритет или создавать заявки.
- Данные заявки и история изменения записываются одной транзакцией `BEGIN IMMEDIATE`. Изменение выполняется условным UPDATE `WHERE id=? AND version=?`, затем версия увеличивается.
- При конфликте возвращается 409, частичные изменения не сохраняются.
- Комментарии добавляются отдельно и не увеличивают версию заявки, чтобы не создавать лишних конфликтов. Поэтому клиент должен периодически перечитывать историю открытой карточки независимо от версии.
- Время хранится в UTC в ISO 8601. Клиент преобразует его для отображения.

## Ограничения безопасности и масштаба

Параметризованные SQL-запросы, внешние ключи, ограничения CHECK, scrypt для паролей, ограничение JSON, CSP без inline-скриптов, защита CSRF и отклонение чужого Origin. CSV UTF-8 BOM с разделителем `;`; значения, начинающиеся после пробелов с `=`, `+`, `-`, `@`, получают префикс апострофа против формул.

Лимит входа: до 10 попыток с одного адреса за 5 минут; успешный вход сбрасывает счётчик. Хранилище счётчиков ограничено 1000 адресами и существует только в памяти одного процесса. Это не распределённая защита от атак. SQLite WAL подходит для малой учебной системы; постраничной выдачи, фоновых задач, вложений и офлайн-редактирования нет. Сеть не шифруется при HTTP. Демо-пароли известны всем, поэтому нельзя открывать демонстрацию в Интернет.

## Проверка

`python -m pytest -q` из корня проекта. Тесты создают отдельную базу для каждого сценария, используют независимые cookie-сессии, проверяют полный цикл двух ролей, конфликт версий, целостность транзакции, разграничение доступа, CSRF, валидацию, экспорт и сохранение после повторного создания приложения. Это моделирование двух клиентов, а не доказательство испытания на двух физических устройствах.
